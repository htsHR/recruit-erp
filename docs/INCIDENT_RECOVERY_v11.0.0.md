# Recruit ERP v11.0.0 장애 복구 절차

## 공통 원칙

1. 같은 작업을 반복하지 말고 먼저 중단합니다.
2. 화면에 남은 입력과 오류 시각만 기록합니다. 개인정보 원문은 화면 캡처나 채팅에 올리지 않습니다.
3. 브라우저 데이터 삭제, 강제 Import, 전체 복원, Supabase SQL 실행은 관리자 승인 전에는 하지 않습니다.
4. 복구 전 현재 상태의 암호화 안전 백업을 만들 수 있으면 먼저 만듭니다.
5. 원인과 복구 결과를 변경 이력 또는 회사 장애 기록에 남깁니다.

## 저장 실패

1. 입력 화면을 닫거나 새로고침하지 않습니다.
2. 브라우저 저장공간 경고와 시크릿 모드·개인정보 보호 설정을 확인합니다.
3. 불필요한 다른 사이트 데이터만 정리하고 ERP 사이트 데이터는 지우지 않습니다.
4. 다시 저장하기 전 입력 내용을 회사 승인 임시 문서에 보관합니다.
5. 계속 실패하면 관리자에게 알리고 해당 브라우저에서 작업을 중단합니다.

## 클라우드 저장·삭제 실패

1. 로컬 화면에 자료가 남아 있는지 확인합니다.
2. `저장 대기` 또는 `삭제 대기` 건수를 기록합니다.
3. 인터넷 연결 복구 후 `다시 시도`를 한 번 실행합니다.
4. 다른 PC에서 같은 사람을 새로 만들거나 삭제하지 않습니다.
5. 반복 실패하면 대기열을 취소하지 말고 관리자에게 전달합니다.

## 동기화 충돌

1. 충돌 화면의 로컬 값과 클라우드 값을 비교합니다.
2. 최근 시각만으로 결정하지 말고 면접·입사 일정과 담당자 기록을 확인합니다.
3. 사용할 값을 직접 선택합니다.
4. 해결 직후 목록과 변경 이력을 다시 확인합니다.

## 삭제한 자료가 다시 나타남

1. 다시 삭제하기 전에 삭제 대기와 다른 PC의 연결 상태를 확인합니다.
2. 해당 지원자의 ID와 삭제 요청 시각만 기록하고 개인정보는 복사하지 않습니다.
3. 모든 운영 PC의 자동 동기화를 잠시 멈춥니다.
4. 가장 최신 암호화 백업과 변경 이력으로 정상 상태를 결정합니다.
5. 관리자 한 명이 삭제를 재처리하고 다른 PC에서 재등장하지 않는지 확인합니다.

## 브라우저 자료 손실

1. 빈 화면에 새 자료를 입력하지 않습니다.
2. 같은 사이트 주소와 브라우저 프로필인지 확인합니다.
3. Supabase 로그인과 운영 모드를 확인합니다.
4. 클라우드 자료가 정상이라면 먼저 동기화 상태를 확인합니다.
5. 복원이 필요하면 빈 테스트 브라우저에서 백업 검사와 미리보기를 먼저 확인한 뒤 관리자만 적용합니다.

## 잘못된 Import 또는 복원

1. 추가 저장·수정·동기화를 중단합니다.
2. 작업 직전 자동 안전 백업과 현재 상태 백업을 모두 보존합니다.
3. 변경 미리보기와 변경 이력에서 영향 범위를 확인합니다.
4. 관리자만 원상복구를 실행합니다.
5. 복구 후 지원자·사원·학교 건수와 주요 연결 ID를 점검합니다.

## 개인정보 노출 의심

1. 화면 잠금과 로그아웃을 실행합니다.
2. 의심 파일의 재전송·재다운로드를 중단합니다.
3. 비밀번호, 주민등록번호, 계좌번호를 장애 기록에 적지 않습니다.
4. 회사 개인정보 보호 담당자에게 즉시 보고하고 회사 절차를 따릅니다.
5. 관련 계정 세션과 내보내기 감사기록을 확인합니다.

## 배포 장애

1. 새 운영 배포와 GitHub Actions 상태를 확인합니다.
2. 화면 버전, 정적 파일 응답, 브라우저 오류를 개인정보 없는 빈 상태에서 재현합니다.
3. 문제가 확정되면 Vercel에서 직전 검증된 Production 배포로 롤백합니다.
4. 데이터베이스 migration은 별도 되돌리기 계획 없이는 임의로 취소하지 않습니다.
5. 복구 후 운영 주소와 핵심 화면을 다시 확인합니다.

## 권장 복구 목표

- 백업 간격 목표: 영업일 기준 하루 이내. 회사 정책이 더 엄격하면 그 기준을 따릅니다.
- 서비스 복구 목표: 장애 확인 후 2시간 이내를 권장합니다.
- 실제 목표와 책임자는 회사 승인 문서에서 확정해야 합니다.
