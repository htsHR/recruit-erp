# 암호화 백업·복원 운영 안내 — v10.60.0

## 백업 만들기

1. `백업/내보내기`에서 `암호화 전체 백업`을 누릅니다.
2. 12자 이상의 긴 비밀번호를 두 번 입력합니다.
3. `.erpbackup` 다운로드가 끝났는지 확인합니다.
4. 파일은 회사가 승인한 저장 위치에 보관하고 비밀번호는 파일과 분리해 관리합니다.

비밀번호는 서버나 브라우저 저장소에 보관되지 않습니다. 비밀번호를 잊으면 백업을 복구할 방법이 없습니다.

## 복원하기

1. 집 개발·복원 모드에서 `.erpbackup` 파일을 선택합니다.
2. 백업을 만들 때 사용한 비밀번호를 입력합니다.
3. 데이터 종류, 현재 건수, 파일 건수, 신규·변경·누락 미리보기를 확인합니다.
4. 병합, 포함 데이터 전체교체 또는 전체 ERP 복원을 선택합니다.
5. 현재 ERP의 암호화 안전 백업이 다운로드되었는지 확인하고 한 번 더 승인합니다.
6. 로컬 적용 결과를 확인한 뒤 Supabase 저장은 기존 백업센터 절차에 따라 별도로 확인합니다.

잘못된 비밀번호와 손상된 파일은 같은 안전 메시지로 차단합니다. 암호화 오류의 세부 값, key, salt, IV, ciphertext와 복호화된 JSON은 화면·콘솔·감사로그에 출력하지 않습니다.

## 이전 평문 JSON

`고급 메뉴 · 이전 평문 JSON 내보내기`는 구버전 업무 호환을 위해 한시적으로 유지합니다. 평문 파일은 메모장으로 열어 내용을 읽을 수 있으므로 관리자만 승인된 위치에서 사용해야 합니다. 기존 `.json` 복원은 가능하지만 암호화되지 않은 이전 백업이라는 경고가 표시됩니다.

## 암호화 파일 구조

바깥 봉투에는 다음 정보만 있습니다.

- `format`: `recruit-erp-encrypted-backup`
- `cryptoSchemaVersion`: `1`
- 앱 버전
- PBKDF2-SHA-256 반복 횟수와 base64 salt
- AES-GCM base64 IV
- base64 암호문 payload

payload 안에는 기존 `recruit-erp-backup` schemaVersion 2 JSON이 그대로 들어갑니다. 암호화 봉투와 내부 백업 스키마는 서로 독립적으로 버전을 관리합니다.

PBKDF2는 운영 PC에서 비밀번호 추측 비용을 높이면서 사용자가 수 초 이상 기다리지 않도록 310,000회로 정했습니다. 실제 가상 대용량 테스트의 처리 시간은 CI와 변경 기록에서 계속 확인합니다.

## 장애 복구

- 암호화 백업 생성 실패: 입력값과 ERP 데이터는 바뀌지 않습니다. 최신 브라우저와 저장공간을 확인한 뒤 다시 시도합니다.
- 비밀번호 오류 또는 파일 손상: ERP 데이터는 바뀌지 않습니다. 원본 파일과 정확한 비밀번호를 확인합니다.
- 복원 직전 안전 백업 실패: 실제 적용이 자동으로 중단됩니다.
- 적용 중 저장 실패: 메모리에 보관한 작업 전 스냅샷으로 원상복구합니다. 다운로드한 안전 백업도 보관합니다.
- 페이지 닫힘·새로고침: 메모리의 비밀번호가 사라지는 것이 정상입니다. 파일을 다시 선택하고 비밀번호를 다시 입력합니다.

## 운영·권한

- 관리자/로컬 관리자: 암호화 전체 백업과 집 모드 복원 가능
- 채용담당자: 정책상 허용된 일반 내보내기만 가능
- 조회 전용: 백업·복원 불가
- 회사 모드: 백업 생성 가능, 파일 검사·복원·병합·전체교체 불가
- 집 모드: 관리자 확인 후 파일 검사·미리보기·복원 가능

실제 개인정보와 운영 백업은 테스트, GitHub Actions secret, artifact, 로그에 넣지 않습니다.
