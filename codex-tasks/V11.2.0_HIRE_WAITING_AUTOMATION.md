- 권장 브랜치: `agent/v11.2.0-hire-waiting-automation`

## 1. 목표
입사대기자 명단에서 반복 수기입력을 줄이기 위해 다음 P0 기능을 구현합니다.

1. 입사월 기준 사원번호 자동채번
2. 생년월일 순서 기반 채번
3. 기존 사원번호 절대 보존
4. 사원명부 포함 중복 사원번호 방지
5. 생년월일 확인 필요자 자동 제외
6. 경력직 비고 자동작성
7. 신입 키/몸무게 비고 자동작성
8. 기존 수기 비고 절대 덮어쓰기 금지
9. 적용 전 미리보기
10. 화면 조회/미리보기만으로 데이터 변경 금지

사용자 기능명은 **`사번·비고 자동작성`** 으로 합니다.

대규모 재설계 금지.

## 3. 자동사번 형식
형식:

`S + 입사연도 2자리 + 입사월 2자리 + 순번 3자리`

예:
- 2026년 8월: `S2608001`, `S2608002`, `S2608003`
- 2026년 9월: `S2609001`, `S2609002`

월이 바뀌면 해당 월 기준으로 `001`부터 사용 가능 번호를 다시 계산합니다.

## 4. 자동작성 대상 범위
입사대기 화면에서 특정 날짜를 선택했더라도 자동작성 계산 대상은 **그 날짜가 포함된 월 전체**입니다.

예: 선택일 `2026-08-10` → `2026-08-01 ~ 2026-08-31`

대상 조건:
- `normalizeStatus(applicant.status) === '입사예정'`
- `applicant.hireDate`가 해당 `YYYY-MM`에 속함

그 외 상태는 제외합니다.

## 5. 기존 사번 보호
이미 `employeeNo`가 있는 사람은 자동사번을 다시 부여하지 않습니다.

예:
- 김철수 `S2608001` → 유지
- 박민수 빈값 → 신규 채번
- 이영희 `S2608003` → 유지

생년월일순을 맞추기 위해 기존 번호를 재정렬/재채번하면 안 됩니다.
수기 `employeeNo`가 최우선입니다.

## 6. 중복번호 방지
신규 번호 생성 시 다음을 모두 확인합니다.

1. `hireWaitingProfiles` 전체
2. 현재 계산 대상 입사대기자 전체
3. `employees` 사원명부 전체

대소문자는 동일 번호로 취급합니다.

해당 월 `SYYMM001 ~ SYYMM999` 중 실제로 사용되지 않은 **가장 작은 번호**를 순서대로 사용합니다.

예: `001`, `003` 사용 중이면 첫 신규 대상은 `002`, 다음은 `004`.

## 7. 신규 채번 정렬
`employeeNo`가 비어 있는 신규 대상끼리만 아래 순서로 고정 정렬합니다.

1. 생년월일 빠른 순
2. 이름 가나다순
3. `applicantId`

동일 데이터에서 결과가 매 실행마다 달라지면 안 됩니다.
한국어 이름 정렬은 안정적으로 처리합니다.

## 8. 생년월일 규칙
자동사번의 대상 판정과 정렬에 **주민등록번호를 절대 사용하지 않습니다.**

기존 `residentNumber → 생년월일` 함수가 있어도 자동채번에는 사용 금지입니다.
지원자의 기존 `birthYear`/생년월일 필드만 사용합니다.

허용 가능한 완전한 날짜 예:
- `2000-05-20`
- `20000520`
- `2000.05.20`
- `2000/05/20`

제외:
- `2000년생`
- `2000`
- `00.05`
- 빈값
- 세기를 확정할 수 없는 `YYMMDD`
- 실제 달력상 존재하지 않는 날짜

불완전한 대상은 사번을 부여하지 않고 미리보기 상태를 **`생년월일 확인 필요`**로 표시합니다.
정상 대상의 자동채번까지 막지는 않습니다.

## 9. 비고 자동작성 우선순위
`profile.remarks`가 한 글자라도 존재하면 절대 변경하지 않습니다.

우선순위:
1. 기존 `profile.remarks` → `수기 비고 유지`
2. 경력직 `career`
3. 신입 키/몸무게
4. 자료 없으면 빈값 유지

`applicant.memo` fallback과 실제 `profile.remarks` 수기값을 혼동하지 않습니다.
기존 memo를 자동으로 remarks에 복사하지 않습니다.

## 10. 경력직 비고
기존 `applicant.careerType`, `applicant.career`를 재사용합니다.

기존 ERP 기준에서 경력직으로 판단되고:
- `profile.remarks`가 빈값
- `career`가 존재

하면 `career.trim()`을 자동 `remarks`로 사용합니다.

예:
- `careerType = 경력`
- `career = 반도체 설비 PM 2년`
- 결과 `remarks = 반도체 설비 PM 2년`

`경력직:` 같은 임의 접두어는 붙이지 않습니다.
`career`가 비면 내용을 만들어내지 않습니다.

## 11. 신입 키/몸무게
먼저 최신 main에 의미가 같은 기존 필드가 있는지 확인합니다.

있으면 재사용.
없으면 Supabase migration/신규 테이블 없이 `hireWaitingProfiles`에 선택 필드만 최소 추가합니다.

- `heightCm`
- `weightKg`

검증 범위:
- `heightCm`: 100~250
- `weightKg`: 30~250

둘 다 정상일 때만 `182cm/78kg` 형식의 자동 비고를 만듭니다.
둘 중 하나만 있거나 범위를 벗어나면 자동 비고를 만들지 않습니다.

## 12. 키/몸무게 UX
기존 23열 입사대기 표에 큰 신규 열 2개를 추가하지 않습니다.

권장 UX:
`사번·비고 자동작성` 미리보기 안에서 신입 + 비고 빈 대상에만 `키(cm)`, `체중(kg)`을 간단히 입력합니다.

입력값은 **적용 전까지 저장 금지**.
취소하면 완전히 폐기합니다.

## 13. 미리보기
입사대기 화면에 `[사번·비고 자동작성]` 버튼을 추가합니다.

클릭 시 데이터 수정 없이 메모리 계산만 합니다.

요약 예:
- 전체 대상 18명
- 기존 사번 7명
- 신규 채번 10명
- 확인 필요 1명
- 비고 자동작성 6명

표 예시 컬럼:
- 성명
- 입사일
- 현재 사번
- 변경 후 사번
- 키/체중(필요 대상만 입력 가능)
- 비고 처리
- 상태

하단: `[취소] [적용]`

미리보기 단계 금지:
- localStorage 저장
- `hireWaitingProfiles` 변경
- `applicants` 변경
- `employees` 변경
- shared-storage PUT
- 공용 master 변경
- revision 증가
- audit log 저장

취소 시 변경 0건이어야 합니다.

## 14. 적용
사용자가 `[적용]`을 눌렀을 때만 실제 변경합니다.

수정 가능 항목:
- `employeeNo`가 빈 대상의 `employeeNo`
- `profile.remarks`가 빈 대상의 자동 `remarks`
- 필요한 경우 `heightCm`
- 필요한 경우 `weightKg`

기존 값 덮어쓰기 금지.

전체 변경안을 메모리에서 먼저 계산하고 다음을 검증한 뒤 한 번에 저장합니다.
- 사번 중복
- 날짜 유효성
- 입력값 유효성
- 권한

저장 전 기존 `hireWaitingProfiles`를 보존합니다.
저장 실패 시 **전체 rollback**하고 부분 성공을 남기지 않습니다.

성공 후 현재 입사대기 화면을 재렌더링하고 toast 예:
`사번 10명 · 비고 6명 자동작성 완료`

## 15. 권한
새 권한체계를 만들지 않습니다.
기존 입사대기 수정 권한(`employee.write` 등 실제 코드 기준)을 재사용합니다.
조회전용 사용자는 적용할 수 없습니다.
`sensitive.read`를 확대/약화하지 않습니다.

## 16. 공용폴더 저장 연동
PR #17에서 반영된 기존 공용저장 흐름을 그대로 사용합니다.

`입사대기 데이터 변경 → 기존 localStorage 저장 → 기존 shared-storage → ERP Bridge → ERP_DATA/erp-data.json`

새 Bridge API/새 공용폴더 파일/새 저장 서비스 금지.
가능하면 `shared-storage` schemaVersion도 변경하지 않습니다.

`residentNumber`는 계속 공용 snapshot에서 제외합니다.

## 17. ERP Bridge 수정 금지
이번 task에서는 다음을 수정하지 않습니다.
- ERP Bridge 실행파일/빌드 로직
- `bridge-config.json` 구조
- localhost port
- Origin/token 정책
- rootPath
- backup/revision/lock 정책

필요해지면 자동 배포를 중단하고 보고합니다.

A. 8월 신규 3명, 기존 번호 없음 → `S2608001~003`

B. `001`, `003` 사용 중 + 신규 2명 → `002`, `004`

C. employees에 동일 사번 존재 → 중복 생성 금지

D. 기존 `employeeNo=S2608007` → 자동화 후 동일 유지

E. 생년월일 없음/불완전 → 채번 제외 + `생년월일 확인 필요`

F. 기존 `profile.remarks` 존재 → 한 글자도 변경 안 됨

G. 경력직 + `career=반도체 설비 PM 2년` + remarks 빈값 → career 자동 비고

H. 신입 + `heightCm=182`, `weightKg=78` + remarks 빈값 → `182cm/78kg`

I. 키 또는 체중 한쪽만 있음 → 불완전 자동비고 생성 금지

J. 미리보기 후 취소 → localStorage/arrays 변경 0

K. 저장 실패 → 전체 rollback / 부분 저장 없음

L. 같은 데이터로 여러 번 미리보기 → 사번 계산 결과 동일

기본 검사:
- `npm run check`
- UI를 변경했으므로 기존 `npm run test:ui-layout`이 존재하면 실행
