# Recruit ERP

[![ERP 자동 검사](https://github.com/htsHR/recruit-erp/actions/workflows/quality-checks.yml/badge.svg?branch=main)](https://github.com/htsHR/recruit-erp/actions/workflows/quality-checks.yml)

채용 지원자, 일정, 사원명부와 협력학교를 관리하는 웹 ERP입니다. 현재 운영 버전은 **v10.63.0**입니다.

운영 홈페이지: https://recruit-erp.vercel.app

## 매일 사용할 때

1. 화면 왼쪽 아래에서 클라우드 상태를 확인합니다.
2. `동기화 정상`이면 평소처럼 사용합니다.
3. `저장 대기` 또는 `삭제 대기`가 보이면 인터넷 연결 후 `다시 시도`를 누릅니다.
4. `삭제 대기 확인`에서 아직 클라우드에 반영되지 않은 삭제 요청을 확인할 수 있습니다.
5. `충돌 확인`이 보이면 두 자료를 비교하여 사용할 정보를 선택합니다.
6. 중요한 대량 수정 전에는 `백업/내보내기`에서 암호화 전체 백업을 받습니다.

## 자료를 안전하게 다루는 규칙

- 실제 지원자·사원 정보는 테스트에 사용하지 않습니다.
- 업데이트 검사는 `테스트지원자`처럼 만든 가상 자료만 사용합니다.
- JSON Import 전에는 변경 미리보기를 확인합니다.
- CSV 파일을 열었을 때 수식처럼 실행될 수 있는 값은 자동으로 일반 문자 처리됩니다.
- 공용 컴퓨터에서는 사용 후 로그아웃하고 개인정보 화면 잠금을 사용합니다.
- `<img ...>` 같은 문자열이 이름이나 메모에 들어와도 프로그램으로 실행되지 않고 글자로만 표시됩니다.
- 출처가 불분명하거나 ID 검사에 실패한 JSON 파일은 가져오지 않습니다.

## 업데이트 자동 검사

GitHub에 변경 요청이 올라오거나 `main`에 코드가 합쳐지면 다음 항목을 자동 검사합니다.

- 브라우저 저장 실패 안전장치
- 사원 JSON Import의 빈값 보호와 변경 미리보기
- 모든 CSV 내보내기의 수식 실행 방어
- 개인정보 화면 잠금과 내보내기 기록
- 클라우드 충돌 감지와 전송 재시도 대기열
- 클라우드 삭제 대기·실패 재시도·화면 재등장 방지
- 인라인 실행 속성 차단, JSON/ID 검사와 CSP 보안 정책
- 외부 Supabase 라이브러리 버전·무결성 고정
- 관리자·채용담당자·조회전용 역할표와 주요 저장 경로 권한 검사
- 조회 전용 수정·삭제 차단과 Supabase RLS 정책 파일
- AES-GCM 암호화 백업 round-trip, 변조·오류·크기 제한과 레거시 JSON 호환성
- 전체 JavaScript 문법
- 화면·프로그램·변경 기록의 버전 일치
- Vercel 보안 응답 설정
- Playwright 기반 5개 뷰포트와 125% 확대·주요 화면·3개 역할 UI 회귀 검사
- 오늘 연락·면접·결과·D-3 입사·출근·14일 정체 자동 분류와 5,000명 성능 검사
- 입사·온보딩 9단계, 미제출 서류, 사번 중복, 1회 전환과 입사 취소 검사

### 로컬 테스트

개발 컴퓨터에서는 Node.js 20 이상과 Chrome 또는 Edge를 준비한 뒤 아래 명령을 실행합니다.

```text
npm ci
npm run check
npm run test:ui-layout
```

로컬 UI 스크린샷은 기본적으로 `artifacts/ui-v10.63.0`에 저장됩니다. 테스트 데이터는 이름·연락처·학교가 모두 가상인 전용 자료만 사용합니다.

### GitHub CI 테스트

Pull Request와 `main` 변경에서는 GitHub Actions가 의존성을 설치하고 Noto CJK 한글 글꼴 캐시를 준비한 뒤 `npm run check` → `npm run test:ui-layout` 순서로 실행합니다. UI 검사 실패도 병합 검사 실패로 처리하며, 성공·실패 여부와 관계없이 한글이 표시된 화면검사 스크린샷을 `ui-layout-screenshots-<실행 시도 번호>` artifact로 14일간 보관합니다.

## 안전한 업데이트 순서

1. `agent/...` 작업 브랜치에서 수정합니다.
2. 가상 데이터로 `npm run check`를 통과시킵니다.
3. GitHub 변경 요청에서 자동 검사와 Vercel 미리보기를 확인합니다.
4. 문제가 없을 때만 `main`에 병합합니다.
5. 운영 홈페이지의 화면 버전과 주요 기능을 확인합니다.

## v11.0.0 실제 운영 준비 — 릴리스 후보

- 관리자 전용 운영 준비 화면에서 자동 안전 점검과 사람이 직접 해야 하는 모의훈련을 구분합니다.
- 화면·보안·암호화 백업·권한·변경 이력·동기화 대기·저장공간·가상 6,500건 성능을 자동 확인합니다.
- 권한·RLS와 유출 비밀번호 보호 확인은 Supabase cloud admin 상태에서만 체크할 수 있으며, 나머지 모의훈련도 30일 단위로 확인합니다.
- 필수 모듈은 누락이나 실제 기능 시험 실패 시 자동으로 실패 처리합니다. 암호화는 가상 문자열 AES-GCM round-trip을 사용합니다.
- 개인정보 원문이 없는 운영 준비 보고서를 JSON으로 저장할 수 있지만, 로컬 보고서는 READY가 될 수 없고 전자서명된 증명서가 아닙니다.
- 예전 Supabase 공개 보안 함수의 직접 실행 권한을 닫는 migration 후보를 포함합니다. 사용자 승인 전에는 운영 DB와 `main`에 적용하지 않습니다.
- 실제 적용 migration, 읽기 전용 verification, 관리자 승인 후에만 쓰는 rollback SQL을 분리합니다.
- 운영자 설명서, 장애 복구 절차와 최종 릴리스 점검표를 제공합니다.

자세한 내용은 `CHANGELOG_v11.0.0.md`, `docs/OPERATOR_GUIDE_v11.0.0.md`, `docs/INCIDENT_RECOVERY_v11.0.0.md`, `docs/RELEASE_READINESS_v11.0.0.md`를 확인하세요.

## v10.63.0 입사·온보딩 관리

- 입사 취소 사유를 남기고 취소 대상을 진행 목록과 분리합니다.
- 온보딩 화면에는 입사대기자의 주민등록번호를 표시하지 않습니다.
- 새 저장 키·Supabase 테이블·RLS 변경 없이 기존 입사대기 프로필을 확장해 사용합니다.

## v10.60.0 암호화 백업·복원

- 전체·지원자·사원·학교·입사대기 백업을 `.erpbackup` 암호화 파일로 저장합니다.
- AES-GCM 256비트와 PBKDF2-SHA-256 310,000회를 사용하며, 파일마다 새로운 salt와 IV를 만듭니다.
- 비밀번호와 암호화 키는 localStorage, sessionStorage, IndexedDB, 감사로그에 저장하지 않습니다.
- 암호화 파일은 메모리에서 복호화한 뒤 안전 트리·행 ID·기존 백업 구조·건수·FNV 무결성 검사를 모두 통과해야 미리보기가 열립니다.
- 복원 직전에는 같은 비밀번호로 현재 ERP의 암호화 안전 백업을 먼저 다운로드합니다.
- 기존 평문 JSON은 이전 업무 호환을 위해 관리자용 고급 메뉴와 레거시 복원으로만 유지합니다.

사용법과 장애 복구 절차는 `docs/ENCRYPTED_BACKUP_v10.60.0.md`, 변경 내역은 `CHANGELOG_v10.60.0.md`를 확인하세요.

## v10.57.0 사용자 권한 설치

화면 코드 배포만으로는 서버 권한이 완성되지 않습니다. Supabase 프로젝트의 SQL Editor에서
`supabase_migration_v10.57.0_rbac_rls.sql`을 한 번 실행해야 합니다.

1. SQL 실행 결과에서 가장 먼저 만든 Auth 계정이 `admin`인지 확인합니다.
2. ERP에 관리자로 로그인합니다.
3. `시스템 → 사용자 권한`에서 다른 계정을 `채용담당자` 또는 `조회 전용`으로 지정합니다.
4. 조회 전용 테스트 계정으로 로그인하여 수정·삭제·복원 요청이 거부되는지 확인합니다.

서버 SQL을 적용하기 전에는 ERP에 `Supabase 권한 SQL 적용 필요` 경고가 표시됩니다.

## 문제가 생겼을 때

- 화면 버전이 예전이면 `Ctrl + F5`로 새로고침합니다.
- 저장 실패 메시지가 나오면 화면을 닫거나 초기화하지 말고 먼저 JSON 백업을 받습니다.
- 동기화 실패 시 로컬 자료와 저장·삭제 요청은 유지되며, 인터넷 복구 후 다시 시도할 수 있습니다.
- 새 버전에서 큰 문제가 생기면 GitHub의 직전 정상 병합 커밋으로 Vercel을 되돌립니다.
- 백업 복원은 반드시 미리보기와 가상 데이터 검증 후 진행합니다.

## 알려진 제한

- 처음 v10.53 이상을 실행하는 브라우저에는 과거 동기화 기준점이 없습니다.
- 삭제 요청을 취소하면 서버에 남아 있던 자료가 다음 동기화에서 다시 나타날 수 있습니다.
- Supabase 권한 SQL을 적용하지 않은 프로젝트에서는 서버 역할 분리가 작동하지 않습니다.
- 로컬 전용 모드는 Supabase 계정 권한과 별개이며, 그 브라우저 안의 데이터만 관리합니다.
- CSP는 인라인 JavaScript를 차단하므로 새 화면 버튼도 중앙 이벤트 방식으로 연결해야 합니다.

버전별 상세 내용은 저장소의 `CHANGELOG_v*.md` 파일에서 확인할 수 있습니다.
